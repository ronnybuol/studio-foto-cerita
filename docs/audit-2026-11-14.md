## Temuan prioritas

P0: wajib diselesaikan sebelum menyatakan siap kelas karena berpotensi kehilangan hasil. P1: penting untuk keamanan/konsistensi saat kelas berlangsung. P2: perbaikan kualitas dan operasional. Prioritas mencerminkan dampak; masalah statis di bawah belum semuanya direproduksi melalui browser dengan D1 nyata.

### A01 — P0: hasil lokal setelah simpan gagal dapat tertimpa server

Lokasi: public/app.js, saveAnswer (sekitar 753), restoreParticipantSession (sekitar 1653), dan handler simpan story/edfat/caption/etika.

saveAnswer mengganti state.work[key] dengan payload final sebelum PUT, lalu menelan error dan hanya menampilkan toast. Payload final umumnya tidak bertanda _draft. Saat reload dengan API kembali sehat, restoreParticipantSession mempertahankan lokal hanya jika _draft=true atau story belum completedAt. Hasil final yang PUT-nya gagal tidak memenuhi syarat itu; jawaban server yang lama/kosong dapat menggantinya. Kamera tidak masuk daftar preservasi sama sekali. Tidak ada antrean kirim ulang otomatis atau metadata pengakuan server. Pesan story/edfat dapat menyatakan tersimpan segera setelah memanggil fungsi async, sebelum hasil PUT diketahui.

Perbaikan minimal berikutnya: metadata pending per akun/modul, pertahankan sampai respons sukses untuk versi payload yang sama; saveAnswer mengembalikan status eksplisit; pemulihan mengutamakan pending; retry terkendali saat tersambung. Jangan mengirim ulang payload lama di atas edit baru. Simpan draf tetap lokal sampai pengguna mengirim hasil.

Verifikasi wajib: server berisi versi A, lokal versi B, PUT 500/timeout, reload, B tetap ada dan trainer belum diklaim menerima B; reconnect menyimpan B sekali; pergantian akun tidak membawa pending akun sebelumnya; edit C ketika kirim B berjalan tidak hilang.

Bukti reproduksi terisolasi: fungsi saveAnswer dan restoreParticipantSession asli dijalankan dengan request tiruan. Setelah PUT gagal: captionText = new local B. Setelah restore dari server: captionText = old server A. Ini membuktikan jalur penimpaan pada fungsi asli; belum merupakan tes browser dengan D1 nyata.

### A02 — P1: kegagalan koneksi mengaktifkan demo dan membuka akses modul

Lokasi: syncState, isUnlocked, signup dan cabang !state.online pada kontrol trainer.

Satu kegagalan /state menetapkan online=false. isUnlocked kemudian mengizinkan semua tahap bila tidak locked; signup dapat membuat identitas lokal tanpa token server; trainer dapat mengubah state demo dan melihat toast lokal. Ini sesuai tujuan demo statis, tetapi perilakunya juga berlaku saat produksi sedang gangguan. Latihan dapat diteruskan dengan kesan alur berbeda dari kelas. Nilai locked terakhir memang dipertahankan, jadi ini bukan bukti backend kunci kelas bisa dilewati.

Perbaikan minimal: bedakan demo yang dipilih secara eksplisit dari produksi yang sedang offline. Pertahankan tahap terakhir, draf dan identitas, tampilkan status koneksi tertunda; jangan membuat pendaftaran demo di produksi. Hubungkan dengan A01 agar putus jaringan tidak menghilangkan pekerjaan.

### A03 — P1: username mudah ditebak menjadi satu-satunya kredensial peserta

Lokasi: POST /api/participant-login, validUsername, formulir akun; README mengakui keterbatasan ini.

Username 3–20 huruf pilihan sendiri cukup untuk menerima token baru dan membaca/mengubah jawaban. Token lama dibatalkan. Orang yang mengetahui/menebak username bisa mengambil sesi dan mengganggu peserta asli. Rate limit hanya bertambah untuk username tidak ditemukan dan dihapus pada login sukses; kelas terkunci menutup akses tetapi tidak melindungi saat kelas berlangsung. Jangan mencoba serangan pada peserta produksi.

Pilihan perbaikan: tambah kode pemulihan/PIN akun acak atau batasi pemulihan akun melalui trainer. Rancang kompatibilitas akun lama, cara pembagian kredensial dan alur HP terlebih dahulu. Jangan memaksa daftar ulang atau mereset progres. Sampai diperbaiki, hindari membagikan username dan cetakan daftar internal.

### A04 — P1: tahap dan slide tidak diperbarui atomik; navigasi cepat dapat saling mendahului

Lokasi: bindDashboard handler [data-stage], choosePresentation; PUT /api/state dan /api/presentation.

Pindah modul mengirim perubahan tahap dahulu, lalu presentasi melalui request kedua. LCD yang polling di antaranya bisa membaca tahap baru dengan slide/view lama; jika request kedua gagal, kondisi bertahan. Tombol navigasi teori tidak diserialkan atau dinonaktifkan selama request, sehingga klik cepat dapat memakai state lama atau respons terlambat membalikkan pilihan. Antrean komposisi sudah lebih baik dan sebaiknya dipertahankan. Tidak ada revision untuk menolak respons /state yang lebih lama.

Perbaikan minimal: update tahap dan presentasi awal dalam satu UPDATE endpoint yang sama; antrekan/coalesce kontrol presentasi; tambahkan revisi jika memang diperlukan. Pertahankan kamera, spotlight dan fullscreen. Uji klik cepat, koneksi lambat, request kedua gagal dan dua tab trainer.

### A05 — P1: request tidak memiliki batas waktu; polling bisa berhenti/bertumpuk

Lokasi: request, syncState, refreshLCD dan setInterval.

fetch tidak memakai AbortSignal/timeout. Startup menunggu syncState, sehingga request yang menggantung dapat menahan layar persiapan. refreshLCD memasang lcdPolling sampai request selesai; request yang tidak selesai menghentikan pembaruan berikutnya. Polling peserta memakai interval async tanpa guard in-flight sehingga request lambat bisa bertumpuk dan hasil lama bisa diterapkan belakangan.

Perbaikan minimal: timeout terukur, satu request polling aktif, pemulihan koneksi dan indikator stale. Jangan menganggap timeout PUT membuktikan data belum tersimpan: retry harus idempoten dan mempertimbangkan versi payload (A01).

### A06 — P1: potensi beban baca D1 selama kelas belum terukur

Lokasi: GET /api/state; liveCamera, liveComposition, liveSpotlight; interval frontend.

Peserta aktif polling kira-kira setiap 3,6 detik; LCD sekitar 1,8 detik. /state membaca is_locked, tahap, jumlah peserta dan camera_json tiga kali. Dengan 70 peserta aktif, perkiraan dasar ~70.000 request state per jam, sebelum LCD/trainer dan retry; minimal sekitar enam pembacaan per request setelah cek schema. Ini perkiraan dari kode, bukan pengukuran kapasitas atau tagihan.

Pembacaan camera_json berulang juga berpotensi menghasilkan kombinasi snapshot berbeda ketika trainer sedang mengubahnya. WeakSet migrasi memakai identitas objek binding; efektivitas cache lintas request belum diukur.

Perbaikan kecil yang dapat diuji: baca satu snapshot sesi untuk tahap/kamera/kunci, parse satu kali, hitung peserta terpisah; hindari fetch spotlight bila tidak aktif. Uji beban mencakup polling, submit enam modul, roster, dashboard dan presentasi selama 70 akun aktif. Jangan mengganti stack menjadi WebSocket menjelang kelas tanpa kebutuhan terbukti.

### A07 — P2: validasi payload dan kendali penyalahgunaan belum lengkap

SQL memakai binding dan teks pengguna di banyak jalur utama di-escape; trainer/mentor dibatasi di server; token peserta disimpan sebagai hash. Ini fondasi yang baik.

Namun API jawaban memvalidasi story lebih ketat daripada modul lain. Kamera/komposisi/edfat/etika dapat menerima struktur yang tidak sesuai sehingga render atau penilaian bisa salah. Nilai score etika berasal dari klien dan tidak boleh dianggap penilaian terverifikasi. Request membaca seluruh req.text sebelum batas panjang; JSON salah/terlalu besar menjadi HTTP 500. Registrasi terbuka belum punya pembatasan abuse khusus; rancangan rate limit perlu mempertimbangkan 70 peserta berbagi IP Wi-Fi agar tidak memblokir kelas.

Perbaikan: validasi ringan per modul, kode 400/413 yang tepat, batasi ukuran sebelum/selama pembacaan bila praktis, dan kontrol abuse yang tidak merusak pendaftaran bersama. Uji payload rusak dan XSS pada semua tampilan, terutama spotlight/cetakan.

### A08 — P2: konsistensi draf, storage dan sesi perlu diseragamkan

Kamera/komposisi tidak menyimpan setiap perubahan seperti caption/story/etika. reason komposisi hanya di state sampai Simpan; reload dapat menghilangkan edit yang belum disimpan. Penulisan localStorage tidak ditangani bila kuota/storage diblokir. Pada 401 pemulihan menghapus work lokal; logout juga membersihkan draf. Token invalid akibat login ulang perangkat lain dapat membuat pekerjaan lokal sulit dipulihkan. Storage pekerjaan memakai satu key umum; partisi per akun dan jalur recovery harus jelas.

Perbaikan: draf per akun, fallback/error storage yang terlihat, simpan sebelum logout/401 dan pemulihan tanpa mengirim pekerjaan ke akun lain. Jangan menampilkan status tersimpan jika penulisan lokal gagal.

### A09 — P2: cakupan regresi belum cukup untuk kesiapan lapangan

Workflow load hanya dipicu PR yang menyentuh skrip load atau workflow itu sendiri; perubahan src/index.js, schema dan frontend tidak otomatis memicu tes beban tersebut. Belum ada tes browser nyata untuk gangguan koneksi, restore pending, pergantian cepat trainer, fullscreen dan semua ukuran mobile. Check sintaks hanya tiga file. Tidak ada lockfile pada commit acuan; install audit menghasilkan Wrangler 4.162.0 dari rentang ^4.148.0, sehingga hasil dapat berubah antarwaktu.

Perbaikan: tambah regresi perilaku untuk A01/A02/A04/A05, perluas filter workflow load, pin toolchain/lockfile yang sudah divalidasi. Gunakan lingkungan Linux CI/staging terisolasi untuk integrasi bila workerd Windows tetap gagal. Jangan menandai uji beban selesai dari tes mock.

## Pengalaman belajar dan tampilan

- Struktur 00–06, contoh foto budaya Sangihe, latihan tanpa kamera, catatan fakta dan refleksi etika mendukung tujuan kelas.
- Mode latihan mandiri mempertahankan pekerjaan ketika trainer membuka slide; jangan mengubahnya menjadi perpindahan otomatis yang mengganggu orang menulis.
- Beranda Hong Bit dan kredit tampil di produksi. Formulir mobile dan modul 04/05 lokal dapat dibuka; draf caption lokal pulih setelah reload.
- Story mengizinkan 9 dari 12 kandidat; kandidat 12 merupakan crop foto 5 dan sudah dijelaskan. Pastikan trainer menerangkan bahwa simulasi ini bukan penyerahan sembilan foto orisinal lomba.
- Caption dapat mulai sebelum story lengkap dan minimum submit 50 kata, sedangkan panduan latihan 120–180; ini tidak otomatis bug, tetapi trainer perlu memahami sifat panduan tersebut.
- QR sudah lokal; catatan LCD masih menyebut layanan gambar eksternal, merupakan teks usang.
- Belum tervalidasi: semua slide di proyektor, keyboard mobile, pembaca layar, touch target seluruh modul, warna/kontras seluruh state dan pemulihan lintas perangkat.

Setiap perbaikan memerlukan bukti regresi, npm test/check dan uji alur yang terdampak. Jangan menumpuk desain ulang. Sebelum deployment, verifikasi backup dan target resource; setelah deployment, cocokkan versi aktif serta baca counter/data secara aman. Laporan akhir harus membedakan branch GitHub, CI, pengujian lokal dan Cloudflare. Tidak ada deployment dalam audit ini.
